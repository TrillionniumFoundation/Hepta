## 3. 统一语义与返回借用：修复了什么

原来允许一个 Core v8 被调用函数直接返回借用形参。运行语义会在返回边界创建一个子借用；调用展开器却把返回值直接当成原借用的别名。调用者结束“子借用”时会消费父借用，随后结束父借用被拒绝。父提交上的实际重现得到 `E_HIA_RESOURCE: use of consumed resource parent`。

修正后，仅针对直接转发的借用形参，在被调用函数体之后、按返回值次序显式插入 `borrow.read` / `borrow.mut`。函数内部已经显式创建的子借用不再重复创建。独立语义检查器另行描述隐式返回事件，没有把提议器的输出当作自身的正确答案。

本地冻结源码结果：43/43 回归、零跳过；11 个 profile、158 个登记用例；原程序与展开程序分别执行，合计 Python VM 316 次、Rust VM 316 次、原生代码 316 次，其中 144 次是实际 SIGABRT 路径。原生观测的范围是分配、释放和 abort 的顺序前缀；借用在机器码中被擦除，因此没有虚构“原生借用事件遥测”。

两个对照说明资源线性检查不能代替语义保持：

- 删除子借用的变体仍返回标量 71，但借用开始数和结束数分别由 3 降为 2，被独立事件证明拒绝。
- 交换可变返回借用来源的变体仍满足资源线性约束，但结果由 28 变为 228，被独立语义检查拒绝。

调用展开后的 VM tick 和调用深度可能改变，需要重新核算预算。带循环调用的静态预算例子按合同拒绝为 `E_HIA_BUDGET_UNBOUNDED`；有限执行成功不等于已经得到全程序资源上界。当前结论也不包含任意异常展开、任意异步中断或预算耗尽前缀的普遍等价。

本地 Rust 对照使用身份固定的保留二进制，其 30 个源码与锁文件和当前版本相同，但没有原始构建收据，不能声称本地这次重建或证明源码到二进制可复现。远端 CI 使用其 job 内构建并登记身份的 Rust 产物；第 17 步 build 复用该 job 已准备的 target，不表示这一小步重新编译了全部目标。CI 二进制与本地保留二进制的身份分别记录，不回写本地历史。

## 4. 真实 C++ 版本升级与 ABI

迁移 profile 为 `cpp20-real-gsl-final-action-closed-cv-factories-v3`。实际读取上游 GSL 3.1 与 4.0，通过真实 Clang AST 识别：3.1 的 `const F&` 工厂直接复制，与 4.0 的转发引用、`std::forward` 再平凡复制。检查包含 cv/ref 模板参数、构造函数复制/移动签名以及参数声明身份。原先非 const 左值在两版本中的拒绝/接受差异继续保留。

冻结结果为 18/18 回归、零跳过。6 对原始/迁移后组合，每对有 416 个输入用例；每个输入在原始、迁移两侧各产生一行观测，并各调用 3 个标量入口。因此合计 `6 × 416 × 2 = 4,992` 行正向观测、`4,992 × 3 = 14,976` 次正向标量 ABI 调用。const 用例的 416 行只对应 164 个不同 seed/tag 组合，因为 mode 在这组路径中被忽略；不把重复行写成独立样本。

迁移后生成物与独立 C 调用者运行，迁移后二进制没有链接原始 C++ 对象。C11 `_Generic` 探针检查的是实际生成的 C 定义。同名符号但返回宽度错误（u32）或第三参数有符号性错误（i32）的两个变体，在执行不兼容调用之前就被拒绝。另一个“资源仍线性、功能错误”的变体在 416 行中产生 325 行不匹配。

这些证据覆盖一个真实、有限的闭合标量回调组件，不代表整个 GSL、全部 C++ 模板、STL、异常、任意分配器或文件描述符回调已迁移。手工修复内容和补丁可审计；没有持续记录人工投入，人工工时与总升级成本保持未知。首次开发运行遇到并发源码漂移而失效，保留在 `INITIAL_RUN_REJECTED.json`，没有重新归类成成功样本。

## 5. NDU：决策正确性、预算和实际经济性

### 5.1 原来的两个执行问题

预算在 native 调用之前已经耗尽时，现在直接 abstain，`native_response=null`、`invoked=false`，不会伪造调用收据。身份核对与密封所耗时间从相同额度扣除。共享 runner 在 ownership checks 和 `Popen` 之后启动执行计时器，进程启动和 OS 调度可能使整次调用超过传入额度，因此没有硬实时保证。发布前仍按实测搜索、证明和准备成本，以及提交的预测执行收益，检查剩余预算与净额；这不保证未来执行一定获得真实净收益。

后台任务在排名、候选准备、发布或取消发生异常时，通过 `finally` 保留已经发生的各阶段成本。最近 64 条不可变序列化收据与已结算任务的“提交加 worker 阶段观测耗时累计”分别保留。累计值不会随最近记录被挤出而归零；它不是完整生命周期成本、CPU 时间或整个进程的墙钟时间，并发任务的阶段 elapsed 还可能重叠。排队等待单列，runtime setup/close、收据编码、Future callbacks 和调用方工作还需外层计时。收据明确区分 `execution_status`、记账时 Future 状态与状态范围，避免把“已经执行并记账”误写成 Future 最终状态。

真实取消用例包括 native prepare 已完成后取消：不推进 generation/epoch，持有的活跃 lease 继续返回 173/179，清理完成。该取消用例实际排名总耗时约 13.873 ms、发布阶段总耗时约 166.540 ms，提交加 worker 累计约 181.549 ms。阶段内的 native adapter 与 prepare 耗时已包含在阶段总耗时内，不能再相加。同步机制的 0.157 ms 观测只用于这个机制夹具，不是服务性能结论。

### 5.2 Pareto 并列不再丢掉共同首步

旧调用方在多条完整 Pareto 路径并列时，即使全部被保留、在该有限模型中获准的 Pareto 路径具有相同第一步准备集合，也会因为没有唯一整条路径建议而退回 incumbent。现在只在这些路径的第一步准备集合全部一致时投影该集合；有分歧或 abstain 时保留 incumbent。原始 Pareto 集、DENY_ALL 和验证合同不被改写，也没有声称找到了唯一全局路径。模型的 `verified` 输入是外部断言，不是机器代码安全证明。

正式本地实验 12/12 次 native 调用投影的实际准备集合，都属于相同有限模型下独立精确 DP 返回的最优首步集合。本轮这些集合恰好各只有一个准备集合；这里没有比较或证明完整路径、每条指令或一般程序目标的唯一最优性。其中一个 episode 确实准备并连续执行 Rust，而固定与轻量控制使用 C。因此已出现真实候选分歧，但选择不同并不自动带来收益。

## 6. 强 Rust release 对照与性能诊断

Rust 使用 O3、fat LTO、一个 codegen unit、panic abort、去 frame pointer 和 release 默认溢出策略；C/C++ 使用 O3、thin LTO；Hepta 走现有 O3 Core-to-LLVM 对象后端。LLVM 版本、运行库和链接期 IR 可见范围不同，均有记录，没有把不同编译条件说成相同。

固定 3 个既有长度与 7 个额外保留长度，每个长度、每种后端都有 3 个 seed × 21 个样本；每个样本是一批 64 次调用。120 个测量请求、192 个正确性/资源请求完整保留，无重试、剔除或补样。运行前后源码、工具及生成物身份一致，观察有效；本地是共享主机，不是独占性能实验室。

容差为中位数 ≤ 1.10、p95 ≤ 1.20；10 个点中只有 1 个达到，所有中位比值均大于 1。整个本地性能门未通过。63 个批样本的 p99 实际是本组最大值，不能宣称每次调用的尾延迟保证。

实际机器码诊断发现：所有后端的求和均为标量；C/C++/Rust 的求和主循环每轮展开 8 个字节元素，Hepta 每轮 1 个字节元素并带进位到 abort 的分支。Hepta 的边界与索引递增检查已从主循环消除，不能笼统归因于“所有边界检查”。填充的主向量化循环 Hepta/C/C++ 每轮处理 16 字节，Rust 每轮处理 32 字节；小长度和标量余数路径另有处理。这些差异给出了后续优化候选，尚未通过消融、性能计数器或受控干预分离因果贡献。

不能因为基准 driver 限制 `n ≤ 65536`，就对通用入口加入 `assume` 或直接删除 checked 语义。后续可研究对归纳不变量 `sum_prefix ≤ 255*k` 的证明，或显式受保护条件 `n ≤ floor(U64_MAX/255)` 下使用快路径，其他输入保持 checked fallback；仍需维持分配失败、返回值及释放前缀。这些只是后续设计，没有计入本轮已实现优化。

资源探针在 192 次请求中一致：非空成功路径一次分配、一次释放、最终 live=0；每种后端含 7 个实际分配拒绝用例。C/C++/Hepta 使用 calloc，Rust 使用 malloc 加显式清零；零初始化合同相同，但 libc 路径并不相同。计时样本关闭观测记录，包装分派仍存在；资源探针是独立调用，不能把它说成每个计时样本的完整资源轨迹。

还发现一个未被当前单缓冲内核触发的观测器边界：当 observer 已启用、槽 0 中另有活跃 allocation，且 `realloc(NULL,n)` 成功或 `n==0` 时，默认 `slot=0` 会错误地把该 allocation 记为已释放并清除追踪槽；这段逻辑没有实际调用 `free` 释放那个 allocation。当前工作负载不调用 realloc，本轮所列数据不受该路径影响；在扩展到 realloc 或多个同时活跃 allocation 的资格测试前，必须先修复并独立验证该 observer。采样栈距离也不是整个调用图的栈上界。

## 9. 可信边界与后续工程顺序

本轮独立检查可以拒绝若干真实反例，但可信边界仍包括未形式验证的 Python Core 检查器与导出实现、被选择的 LLVM/链接器、原生加载与运行器、OS/allocator/CPU，以及显式纳入合同的外部代码。选定 Lean 定理、有限 SAT/UNSAT 证明和动态对照各有自己的模型范围，不能累加成整个语言的绝对健全性证明。

下一轮最有判别力的任务顺序是：

1. 建立 checked reduction 的范围/归纳证明与安全快路径，使用已经暴露的保留长度和新增独立负载重新检验 Rust 性能差距；不能降低原有语义换速度。
2. 把 NDU 的 invoke/skip、候选驻留与长期收益建模到真实外部 trace 和部署周期中，寻找预测的盈亏平衡点；先证明有机会回收开销，再扩大规划粒度。
3. 针对 Agent 的实际格式、类型和跨文件行为失败改进表示及结构编辑工具，另行冻结新任务与多模型比较；这次失败不得经人工修补后重命名为原试验成功。
4. 分别建立有界 quiescent state-transfer 验证、活跃版本共享可变状态及外部 alias 的 lifetime/synchronization 合同，以及不可逆外部效果的 durable commit/deduplication 与恢复协议。现有纯标量 immutable generation 的 lease 重叠已实现；本轮取消 trace 展示的是 incumbent lease 与未提交候选共存。Owned-state 切换和 continuation 仍要求没有 active native call 和 live loan；这些机制不能替代跨崩溃的外部 exactly-once。
5. 继续扩展真实 C/C++ 组件并记录人工操作与升级差异；为每个新 ABI 和设备建立单独合同和实机恢复用例。
