# JSON pretty HIA bulk-source r4

## 当前结论

这是保留原有限额的 HIA 源码修订。公开 Core 解析、原生编译和原调用方验证均未执行，因此不构成 JSON/CLI 模块闭合。产品分支 acffa926 未改变，也未删除任何旧实现。

源码 21222 字节，SHA-256 `2a8b2180cb15947c90961a55927241e8198f32a046484127d83b16fa880e9303`；8 个函数、85 个块，单函数最多 47 块，307 条指令，单函数最多 495 个唯一 SSA 名，调用/边参数最多 8 个，公开 f0 返回 u32。

## 实际修复

r3 将字符串和原子字面量批量复制。对有效输入 `"abcd"`、模式 1、输出容量 1，实际 V8 解释运行观察到：r2 返回状态 3 / 错误位置 1；r3 返回状态 3 / 错误位置 6。该差异的原始观察保存在 development/offset-regression.json。

r4 为 span 的容量拒绝计算第一个未能写出的输入字节位置：span 起点加剩余输出容量。其余失败状态保留此前逻辑。批量填充缩进和复制字面量仍使用仓库已有 buffer.fill_range / buffer.copy_range，未添加指令，也未提高编译器或调用方限额。

所有非零状态的输出及长度都必须丢弃。r2 与 r4 的失败前缀及失败长度可以不同；本修订保持的是已准入有效 wire 的状态与错误位置。格式化器仍依赖上游有效紧凑 JSON 准入，不承诺成为一般 JSON 解析器，也不据此宣称任意畸形输入上的诊断优先级等价。

## 已实际执行的开发检查

- 同一组 31 个基线 ID 加 2 个扩展 ID：33/33 V8 IR 执行通过，保留每个输出 SHA 和解释指令数。
- 16 个较小基线正例及一个明确回归例，逐容量覆盖 0 到正确输出长度加 1：477/477 状态、错误位置、诊断状态和保护区比较通过。
- 128 层根深度正例的 8 个明确列出的容量：8/8 比较通过。这 8 个容量不是全部 33283 种容量的穷举证明。
- 差分比较的工作区预填 0x6b，模式字段独立设置，输入及输出/工作区前后保护区逐次检查。

上述解释器把每个批量操作计为一条 IR 操作，指令数和开发环境耗时不代表原生性能。每次 VM 的 60000000 指令防护不是产品时限，也没有替换原生 3/5 秒调用方要求。
