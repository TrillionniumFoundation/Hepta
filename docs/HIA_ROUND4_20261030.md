## 1. 紧凑 typed assembly 进入同一个执行核心

`hepta.hia_agent_assembly` 新增 `hia-asm.v1`，为已有 primitive HIA v6/v7 提供确定性的文本表示。参数、结果、块边、整数模式、效果、借用结束和释放都必须显式给出；整个程序随后经过现有 `verify_program`。该前端没有自动选择运算、插入 cast、补 destructor、修复模型答案或推断任务意图的能力。

可以实际使用的新 CLI 如下；输出使用新文件名，`render`/`import` 不覆盖既有产物。`check-assembly` 只检查语法与 Core 准入，没有创建原生产物或授予部署权。

```sh
hepta hia routes
hepta hia render-assembly program.hia.json -o program.hiaasm
hepta hia check-assembly program.hiaasm
hepta hia import-assembly program.hiaasm -o reassembled.hia.json

hepta hia import-cpp-unique-assignment-project \
  examples/cpp/unique_assignment_project_migration/compile_commands.json \
  --clangxx /path/to/clang++-20 -o assignment.hia.json \
  --report assignment.capture.json
hepta hia import-cpp-unique-assignment-matrix \
  examples/cpp/unique_assignment_project_migration/matrix.json \
  --variant three_weight --clangxx /path/to/clang++-20 \
  -o assignment-matrix.hia.json --report assignment-matrix.capture.json
```

matrix 命令检查所有已登记配置后，才发布 `--variant` 指定的版本；不能只检查一个有利配置。接口定义与入口约束见 [CLI](../hepta/cli.py)、[route inventory](../hepta/hia_routes.py) 和[双 TU 示例](../examples/cpp/unique_assignment_project_migration/)。

| 路径 | 实际执行去向 | 保留的拒绝条件 |
| --- | --- | --- |
| `agent-assembly` / `hia import-assembly` | 文本 → 检查后的 primitive Core → 原解释器或 LLVM 后端 | 旧 schema、nominal composite、未知 opcode、错误类型/资源流、超限输入均拒绝 |
| `hia render-assembly` | 已检查 Core → 文本 → 再次组装和检查 | canonical Core 必须逐字节一致，不能丢弃 exports、属性、顺序或布局信息 |
| Hepta 源码 | `hepta-source` → standalone Core | 有限 checked source profile，要求来源身份 |
| C / C++ 源码与项目 | 已捕获、可表示的子集 → Hepta / 明确项目适配器 → standalone Core | 一般指针程序与未建模资源模式拒绝；legacy native 成功不能代替 standalone 准入 |
| 历史 executable / scalar / composite IR | 各自明确 import 并重新检查 | 需要的来源、版本或适配信息缺失时拒绝 |
| 新 C++ assignment project/matrix | 捕获的限定项目 → Hepta → standalone Core | 旧 unique/composed profile 不被隐式放宽 |
| Rust / TypeScript / Python / Go / 原始 CPU 汇编源码 | 当前没有对应源语言前端 | 作为 HIA 输入明确拒绝；Rust 比较器与 Rust 参考后端不等于 Rust 源码迁移前端 |
| 解释器 / direct LLVM | 同一已检查 standalone Core | 当前原生资格限已测 Linux x86-64；其他目标对象输出需要独立执行资格 |

这使 Agent 可以直接编辑更紧凑的、带类型和资源操作的汇编表示；它尚未建立一般程序逐指令的动态最优规划器。合法的类型和资源流也不等于满足用户的功能规格，例如先做 u32 wrapping 加法再扩大类型，仍可能是类型合法但数学结果错误的程序。

独立资格完成 **81 项 VM 观测和 24 项原生观测**。两个表示样本均保持 canonical Core 与 emitted LLVM 一致：kernel JSON 为 14,572 字节，汇编为 5,690 字节；递归 chain JSON 为 15,029 字节，汇编为 6,734 字节。这里测量的是字节数，token 数未知。原生资格针对 kernel；递归 chain 的 VM 与 roundtrip 证据不能改称该 chain 已取得原生执行资格。资格过程没有请求模型，`agent_advantage_qualified=false`。

## 2. 验证与身份检查仍决定准入

提案继续携带前提、语义保持义务、资源变化和目标约束；guard、narrowing 等变换仍由独立 checker 检查，组合阶段共享整体预算。SAT、unknown、超时、预算耗尽、未支持结构或身份变化均不能取得部署资格。构建记录绑定实际 Core、checker、solver、目标、编译器与最终原生产物；加载检查绑定实际映像。

本轮对密封身份的复用建立在 Linux memfd 的明确条件上：初次读取并核对真实字节后，所持描述符必须继续指向同一个 inode，大小不变，`F_SEAL_WRITE`、`F_SEAL_GROW`、`F_SEAL_SHRINK`、`F_SEAL_SEAL` 全部保留。每次请求前后还核对实际 `/proc/<pid>/exe`。fd 数字复用、seal 缺失、exec 到另一个映像、manifest 漂移、请求或响应绑定错误都会拒绝。

因此节省的是在已检查且不可变的同一产物上反复读取和哈希的开销；没有允许模型、NDU、文本诊断或外部序列化 receipt 自行签发安全证书。NDU 的 `authority: DENY_ALL`、`safety_certificate: false` 保持不变。

资源安全的可证范围是已建模 Core 的线性 owner、loan、显式释放、受检查控制流与效果；验证器实现、后端、所支持的 ABI 和受信外部契约仍构成边界。完整受信链还包括 Core 语义编码、Z3、编译器与链接器、加载器、受控宿主、OS 和硬件。本轮没有证明任意 C/C++ 源程序到 Core 的 refinement，或完整工具链的绝对安全。来源：[NDU 会话身份条件](HIA_NDU_SESSION_COST.md)、[第三轮验证边界](HIA_ROUND3_20261028.md)。

## 4. 真实 C++：替换已存活的组合 owner

新增独立 profile `cpp20-captured-unique-byte-array-move-assignment-v1`。leaf wrapper 必须精确匹配受检查契约：`noexcept`、`this != &other` 保护、真实 `unique_ptr<unsigned char[]>` 移动赋值、长度转移与源长度清零、返回 `*this`；组合类型使用默认的 `noexcept = default` 移动赋值。

不同对象赋值时，先消费旧 destination 并按**成员声明顺序**释放其字段，再将 source 作为新的 destination 绑定；普通析构仍按逆声明顺序释放。literal self move 保持 owner 不变；不同 source 被消费，后续观察和再次移动均拒绝。生成 HIA 不链接原 C++ 对象，旧 profile 仍要求删除 move assignment。

| 配置 | 原生对照用例 | 分配 / 释放 | 分配拒绝 | 最终存活 | 活动项目声明出现次数 | 标准库依赖声明出现次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| three_weight | 789 | 981 / 981 | 337 | 0 | 139 | 92,066 |
| five_weight | 789 | 981 / 981 | 337 | 0 | 139 | 92,066 |

用例覆盖非空 destination 替换、self move、跨 TU 按值消费、零长度、字节边界、每个分配位置的拒绝、部分构造和提前返回。每配置迁移两个项目自由函数，桥接函数为 0，标准库实现体迁移为 0，一般源程序等价证明为 0，性能对照未执行。所有活动声明仍有明确 disposition；标准库声明数量不算作实现迁移量。

两个负向控制分别验证不同性质：删除线性 Core drop 会在产物发布前拒绝；只反转 assignment 的释放顺序虽然资源守恒，实际运行仍被独立生命周期 oracle 检出。后者说明资源平衡不能代替源行为等价。改变 leaf self-move guard 的源契约被拒绝。旧 unique profile 的两个配置各 437 用例回归通过，未借新 hook 放宽旧边界。

本次 Clang 为 **20.1.8**。迁移耗时 **76.297534143 秒**，包含迁移的资格检查为 **82.030602853 秒**，二者不相加；报告峰值 RSS 为 **196,648 KiB**。这些是有限资格成本，不能证明普遍低成本迁移或程序性能优势。测量保留隔离工作快照的准确身份，不宣称最终集成提交已经由该旧快照资格覆盖。发布源码检查点的独立 CI 再次完成两个配置各 789 个原生对照；该平台每配置有 91,300 个标准库依赖声明，与本地的 92,066 分别保存，不能合并成同一个迁移覆盖证明。

仍拒绝 conditional/nested assignment、任意 alias、custom assignment、custom deleter、`reset`、`release` 和 raw-pointer adoption；默认 deleter 标准库仍是显式受信契约。通用 C++ 类布局、mangled symbol 和异常 ABI 未由此保留。

## 6. Agent 三臂：原研究按基础设施规则终止，复制独立登记

原研究使用两个固定模型家族、四个新的维护/API 升级任务和三臂：JSON HIA、compact HIA assembly、Rust，计划 **24 cells**。两个 HIA 表示来自完全相同的初始 canonical Core；所有臂收到完整双文件项目、相同任务信息与生成预算。每 cell 最多两次尝试，每次 2,048 输出 token、完整生成调用 180 秒上限；8,192 context、四线程、greedy seed 0，关闭 prompt cache。超时结束该 cell；基础设施错误使本模型观察无效并停止后续 cells。规则在生成前固定。

| 模型 | 已尝试 / 计划 | 真实 completion 请求 / 完整响应 | 终态 | 正确完成 |
| --- | ---: | ---: | --- | --- |
| Qwen2.5-Coder-1.5B Q4_K_M | 12 / 12 | 20 / 15 | 完整有效观察；5 次生成超时 | **0 / 12**，每臂均 0/4 |

## 7. Owner continuation 与完整成本复测

`continue_queue(token)` 只从内部已知、被取消且有不完整 native prefix 的队列登记尚未执行的 suffix。必须保持同一个 owner/allocation、取消后的准确 revision 和值，并处于无活调用、无借用的安全点。原队列保留 terminal 状态与后继绑定；completed、failed、stale、未知或已继续的队列不能重放。

资格工具和原生回归分别实际执行 **6/40** 与 **22/40** 两个取消位置，后者跨越工作项边界：第一项 17 次完成、第二项 5 次完成。随后选择已证明版本，在同一活 owner 上只执行精确 suffix。取消触发点由夹具注入，prefix/suffix 算术与版本执行均为真实 native 工作。

异常处理已覆盖三个具体问题：事件追加后失败不能留下未发布 continuation；启动 clock 与激活提交、失败恢复都位于同一锁内，不覆盖并发 prepare 新发布的成本债；完成事件失败在真实进度和累计成本结算后才重抛。成功激活后，退出锁或第一次 native 调用前的中断按真实零 prefix 结算。不能取得完整进度或成本时，runtime 标记 poisoned、`cost_accounting_complete=false`，拒绝继续运行，并保留 close 释放 owner。
