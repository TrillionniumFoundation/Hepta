# Native callable registration for canonical Futures

This component adds a private production registration path. The public wrapper,
complete exception diagnostic domain and full BackgroundOptimizer closure remain
open. The component receipt records the exact source, native build and four actual
functional gates; it does not replace the retained original Future campaign.

## Production path

The trusted sidecar initializes the one Future global context, the real X2
resource registry, the one Value context and the one native code owner. Only after
those initializations and nonce bindings succeed does its native policy enable
resource mask 190. No test writes a binding or installs a host callback.

HIAFRQ04 is 128 bytes: operation 0 at byte 8, a borrowed canonical Future Value
capability at bytes 16..39, and a borrowed callable Value capability at bytes
40..63. All remaining bytes are zero. Neither an entry point nor a context pointer
is accepted in this request.

The provider checks the actual resource through Value 49, validates its real
registry record and canonical weak identity, and obtains a strong Future pin
through Value 91. It releases its mutex before calling private FP04 operation 31.
The only callback entry is the statically linked native adapter. Operation 31
requires the separately captured owner source checkpoint in the component receipt;
the four inherited owner/cleanup source files remain owned by that implementation.

## Ownership response

HIAFRR04 is 320 bytes. The provider status is at byte 8 and resource kind 7 is at
byte 16 after a strong pin is published. The owned pin is at bytes 24..47. A known
owned error Value, when returned by the actual Future call, is at bytes 48..71.
Actual Future status and error class are at 72 and 80. Its complete-response flag
is at 88. Provider known, pin-published, pending and registration-attempted facts
are at 96, 104, 112 and 120. Bytes 128..319 preserve the complete actual Future
response after an attempted registration.

Pin publication is independent of cleanup status. The native caller must retain
and eventually consume a published pin even when the provider reports pending.
Unknown or inconsistent custody is not inferred from an error status.

## Actual invocation

The new HIAPFC03 carrier profile retains the real callable as an owner-managed
Value edge before committing callback registration. It promotes the canonical
Future weak identity to an external pin while a callback can execute. The adapter
builds a real one-element tuple containing that exact Future Value, invokes the
actual source-bound callable through Value 70 outside every Future mutex, and
consumes the delivered result and all temporary capabilities by actual ownership
receipts. The original raw callback profile stays separate.

The adapter's HIAFCBR2 response includes the real returned/raised Value and any
unresolved temporary capabilities, mapping/queue/unknown flags, and the first
uncertain Value receipt. The carrier keeps unknown delivery in its actual native
allocation instead of guessing that a capability was consumed.

## Native construction and verification

The callback provider and adapter are composed into a six-body sidecar capsule.
The final product still has 64 logical roles, one physical Value implementation,
one code owner and the original 4 MiB role / 16 MiB text limits.

The actual compiled HIA callback reads its closure and its real argument tuple
through Value operations, then appends the exact Future argument to the actual
closure list. Four native gates compare callback counts with CPython Future:
pending completion, immediate invocation after completion, three registrations,
and cancellation. The caller drops its callable capability before completion.
Each gate checks argument identity, external list retention, final weak staleness,
native registry/queue/capability retirement and the process FD set.

The tests contain no Python production callback handler. The JSON receipt links
the complete native build and actual case records with exact SHA-256 values.
