# Native HTTP protocol metadata

The emitted HIA module makes the original rmcp 3.9.0 protocol-version, legacy/discover lifecycle, and standard HTTP-header decisions. It consumes fresh projections from the captured native HTTP-head and typed SDK roles. Runtime code performs no Rust, Python, C, or shell evaluation.

The HIAHMD01 input has a 64-byte header: magic, mode, raw HTTP-head bytes, HIAHHR01 descriptor bytes, raw JSON bytes, HIASDK01 bytes, captured catalogue bytes, and a zero reserved word. The segments follow in that order. The input is at most 8 MiB, the raw body at most the original 4 MiB, the output at least 8 MiB, and the private work view exactly 44 MiB. Mode 2 requires no raw head, descriptor, or catalogue and a complete 160-byte SDK projection. Bad private frames return 0xfffffffd.

The 128-byte HIAHMO01 output records HTTP status (zero continues), legacy flag, body kind (none/plain/JSON), body size, and the first protocol/session/Last-Event-ID descriptor-row numbers plus one. Words at 64 and 72 retain the actual client-capabilities and experimental.session.workdir JSON spans; the latter exists only for a string. Spans retain the SDK convention: low 24 bits are start plus one, next 24 bits are the exclusive end, relative to the original raw body. The remaining words are zero. Any error body follows at byte 128.

Mode 0 performs protocol-header validation, initialize/body consistency, request metadata consistency, and original lifecycle selection. Mode 1 adds standard headers after the parent has completed the original session lookup; an unknown-session response must keep its earlier precedence. Mode 2 only projects typed capabilities and the optional workdir candidate. Valid per-request metadata capabilities take precedence in mode 2, then initialize capabilities. The parent owns the first tool-call workdir switch, local path checks, allowed roots, and actual IO. This module never authorizes a path.

Duplicate protocol headers retain the original first-value behavior. Standard Mcp-Method and Mcp-Name headers enforce singleton values. Initialize may omit Mcp-Method, but a supplied value must match and duplicate values are rejected. Base64 value decoding uses the exact nine-byte =?base64? prefix, strict canonical padding and unused-bit checks, and valid UTF-8; malformed values preserve the original error. Initialize mismatch diagnostics reproduce UTF-8 lossy replacement. Notification JSON errors omit id, matching the SDK serializer.

The captured tool catalogue is the original fixed 233,965-byte, 11-tool catalogue, SHA-256 b6b8054ce46ae9ceac260e99a3d1beaf5d6c9343bc4c6e5d96281eedd3c3edfd. Its schemas contain no x-mcp-header annotation. The original factory rejects nonidentical external catalogue bytes; the native parent keeps that binding. Thus no Mcp-Param-* header is required for this service. This checkpoint makes no claim to implement arbitrary dynamic schema registration.

Qualification composes actual native HTTP-head and SDK projections with the native metadata role, compared against exact original rmcp functions. All 2,177 cases pass with byte-identical error responses, status and lifecycle selection, plus capability/workdir projection. Cases include malformed/duplicate metadata, known and unknown protocol versions, all accepted header-byte values, strict Base64 and UTF-8, sequence-form capabilities, duplicate workdir keys, integer/string request IDs, omitted notification IDs, a 300,000-element unknown Value, and a 4,000,000-byte unknown string. Another 44 private frame, span, capacity, control and exact 4 MiB cases pass. All 168 selected failures also match the actual frozen old service over real HTTP connections.

The component does not itself close listener/session/SSE/cancellation or the complete service. Its result must be composed with the captured parent and qualified at the full HTTP boundary.
