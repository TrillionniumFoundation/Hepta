# HIA 六项成果：统一源码、实测结果与未通过的验收

本轮已把六项研发工作落实为源码、可执行检查、真实编译与运行记录，交付于
[Draft PR #352](https://github.com/TrillionniumFoundation/Hepta/pull/352)。
当前结论是：**现有 HIA 可以继续作为受检查的语言本体；本轮没有证明它已在
开发效率、完整成本或性能上超过 Rust/C/C++，也没有证明绝对资源安全或全局
指令最优。** 这些结论没有因工程检查通过而被改写。

本报告区分三种结果：实现是否符合所声明的有限规则、实验是否实际完成、
优势是否达到事先登记的门槛。机器可读状态见
[HIA_SIX_OUTCOMES_ACCEPTANCE_20261028.json](HIA_SIX_OUTCOMES_ACCEPTANCE_20261028.json)。

## 2. 安全规格已能检查，但证明边界仍然明确

[安全合同](HIA_SAFETY_CONTRACT.md) 与
[机器矩阵](HIA_SAFETY_CONTRACT.json) 把类型环境、线性 owner、loan 来源与
权限、CFG 合流、调用/返回义务写成可审查规则。资格工具拒绝 registry 漂移、
缺失测试、跳过、失败、运行期间源码改变，以及将未证明的普遍性主张改成 true。

统一源码上的 37 项检查全部通过，且源码在执行前后相同。它们覆盖真实拒绝
路径、原生执行、分配观察与 Rust shadow 对照；通过意味着这些有限检查在
所绑定的源码与宿主上成功，不是对所有程序的 preservation/progress 定理。
完整记录见[统一验收证据](../experiments/hia_six_outcomes/results_20261028/)。

| 问题 | 当前可检查或强制的范围 | 不能外推的保证 |
| --- | --- | --- |
| 类型、所有权、借用 | 精确类型、线性消耗/转移、loan 来源与父子关系、可变别名、CFG 与接口一致性 | 任意指针来源、任意 foreign lifetime 或未建模指令 |
| 正常返回、错误作为值 | 资源必须消费或通过已检查签名转移；失败分配仍产生须消费的逻辑空 owner | 通用异常展开或任意析构恢复 |
| trap、预算停止、取消 | VM 保留停止时账本；已实现的协作式任务按显式状态转换清理；native trap 终止 | VM 停止不是原生资源配额，也不是异步取消/信号展开语义 |
| 递归与并发 | Core 可维持已支持的递归资源规则；有限分析在不支持时拒绝或返回未知；host 在安全点受锁约束地切换 | 一般终止性、native 栈字节上界、共享可变内存/atomics/MMIO 的通用内存模型 |
| 静态资源预算 | 审计过的有限 profile 可重新计算请求的 live payload、部分分配事件、tick 或调用深度 | allocator 元数据、碎片、foreign 分配、编译器内存与进程 RSS |
| 运行时资源管理 | 限制已准入映像、准备过程、未决释放债务与有限队列；不确定释放继续记账 | 任意 native 进程的总内存上界 |
| 源码→Core | 支持 profile 内的检查与再次 Core 验证 | 完整源码语义保持证明 |
| Core→LLVM→机器码 | 直接 LLVM 路线、实际原生差分与资源观察 | 完整后端 refinement 证明；编译器、链接器、loader、OS、硬件仍在可信基础内 |

以下八项保持 false：完整语言健全性、源码到 Core 的 refinement、Core 到
native 的 refinement、全局最优、绝对资源安全、一般并发内存安全、native
进程内存上界、普遍超过 Rust 的性能。AI、NDU、哈希和元数据都不能替代准入
检查或自动把这些主张升级为已证明。

## 3. 迁移：实现体、功能、资源、维护与成本

### filecheck：新的真实文件校验纵向案例

[filecheck 源码](../examples/hia_filecheck/) 是有实际输入、文件读取和校验输出
的 CLI。C 宿主保留文件 I/O、装载和标量打包；迁移目标是两个 C 翻译单元中的
**2 个实现体、33 行、1,138 字节**。它们经 Clang 捕获、结构化 AST 翻译、
Hepta 源码、独立 Core 准入与 LLVM 生成原生库；目标没有链接原 C 实现对象。
这是新编写的小型组件，不是从一个庞大历史项目自动迁出的应用。

在统一源码上完成：

- 96 个差分输入、8 条原生路线，共 768 次功能/标量 C ABI 调用。
- 48 组资源案例，每组比较 VM、原 C 与 native HIA，包含成功、非法输入与
  分配拒绝；完成路径的 live owner 为零。
- ABI 资格限于 Linux x86-64 LP64 的标量公共接口；未把 foreign raw pointer
  或借用资源描述符暴露为自动安全的 C ABI。
- 维护任务增加第三个翻译单元与命名算法 API，迁移实现体增至 3 个；对有效
  算法和拒绝输入进行了差分检查，手工修改目标源码为 0 次。
- 本地宿主成功切换与拒绝 staged load 后均保持正确摘要；实测切换段分别为
  45,784 ns 与 14,983 ns。这是本地装载边界证据，不赋予 NDU 生产发布权。

初次捕获/迁移耗时 **3.748342 s**，独立再次准入 **0.012340 s**，维护流水线
**10.965954 s**，完整资格过程 **34.708882 s**。这些是机器执行成本；没有
计量人工开发、调试与长期维护，因此“0 次目标手改”不能换算成劳动节省。
原 allocator 替换等价性、任意 C/C++ 语义与完整源语言 refinement 仍是未证明项。

### C++：真实标准库所有权契约的多文件重验

既有 `std::unique_ptr<unsigned char[]>` 默认 deleter 案例在统一源码上重新执行：
2 个翻译单元、2 个构建配置，共捕获 4 条编译命令。每配置记录 2 个项目函数
实现、跨单元按值 owner 转移、构造失败、move 前后提前返回、范围错误和析构。

每个配置的原 C++ 与独立 HIA 路线各执行 **437 个案例**，观察均为
**401 次分配、401 次释放、196 次拒绝、0 个 live 资源**；两配置摘要分别为
`79fca1db8d2f0865` 与 `dd7575852bb30d54`。移除必要 drop 的两个反例均在
Core 准入时拒绝，没有生成目标制品。

每配置出现的 **92,058 条标准库声明记录是依赖清单，标准库函数体迁移数为 0**。
此项使用明确的 unique_ptr 契约，不代表自动重写了 libstdc++，也不声称保持
任意 C++ 类布局或 mangled ABI。保留的是已验证的标量 C ABI。

实测迁移 **116.552964 s**、完整资格 **123.046415 s**；没有运行这项 C++
案例的性能比较，人力成本为未测量。原捕获程序流式读取了 Clang AST，但没有
保留原始 AST stdout；记录中的哈希不能重建这些未保留的字节。完整附件覆盖
所有实际保留输出，不能声称包含未留存的原始 AST。

C++ 原报告未直接写入 Git HEAD 字段。此次源码归属由 7 项显式文件绑定、
与统一提交一致的 140 文件编译器集合哈希，以及捕获的项目输入共同核对；
没有向原始记录补造当时不存在的 Git 字段。

## 4. NDU：完整冷成本净收益为负，暖差异缺少优化归因

按照同一冻结候选信息与预算，实际比较强固定方案、完整有限 DP 与原生 NDU。
协议完整执行一次：36 个控制层 episode、1,152 次 query、27 个应用 episode，
252 次原生加载执行均有 fresh independent proof；输出与真实 compile-credit
约束全部 admitted，没有剔除样本。完整冷构建为 **47.610866564 s**。
数值与逐项决策见 [NDU 证据](../experiments/hia_ndu_net_value/results_20261028/README.md)。

| 应用场景 | 强固定，秒 | 完整 DP，秒 | NDU 暖成本，秒 | NDU 冷成本，秒 |
| --- | ---: | ---: | ---: | ---: |
| 稳定复用 | 24.705403 | 23.865143 | 24.706518 | 72.317384 |
| 负载变化 | 30.879912 | 28.914087 | 27.926390 | 75.537256 |
| 共享编译预算 | 43.472299 | 43.881308 | 42.693707 | 90.304573 |

每行按一个独立部署解释，各自计算一次公共准备；**不能直接相加**。组合工作
负载只计一次公共准备时，固定、DP、NDU 暖、NDU 冷分别为 **65.123898、
62.726822、61.367863、108.978729 秒**。暖成本仅排除该原生控制器冷构建，
仍计入登记范围内的证明、编译、准入、映像检查、执行、记录与关闭。工具链
安装、既有依赖源码缓存的取得与最终汇总归档属于已声明排除项。
外层研究驱动的 Python 进程启动、imports/argparse，以及最终 envelope / aggregate
序列化也未计入；这里的“完整”始终指登记的成本范围，不能解释成全部工程投入。

**NDU 在九个应用 episode 中构建的优化候选为 0。** 全部 27 个 episode
仅有一次候选编译，发生于 DP 的共享预算场景；该 `guard-small` 被选择 5 次，
其余 211 个 module-target 决策均为 `base`。因此 NDU 暖组合成本的微小下降
不能解释为发现了更好的优化，也不能推出长期盈亏平衡点或统计优势。

共享预算使用同一 kernel 的两个独立实例，不是两个异质源码组件。实际执行
了一个 compile-attempt permit 的约束，但大部分选择 base，未充分激活多个
有利机会之间的预算竞争；六个 epoch 也不等于长期部署证明。

控制层机制方面，sealed session 暖成本 **1.282943 s**，低于重复完整哈希的
**1.835127 s**，但仍高于完整 DP 的 **0.790015 s**；加 exact advisory cache
后为 **1.570831 s**，本轮反而更慢。缓存默认关闭，`authority=DENY_ALL`、
`safety_certificate=false` 保持不变。注册的完整成本优势 gate 为 **false**。

## 5. Agent：真实校准失败，主对照尚无数据

新的实验框架覆盖多文件、API 升级、所有权/资源修复与维护，并使 full/query
两种呈现允许修改相同的完整函数体。query 提供可编辑函数和不可改接口摘要，
不是单节点图编辑；四份物理 HIA 文件组合成一个 Core 模块，不代表独立目标
模块链接。公共反馈与最终隐藏验证分开，另有 provider 检查，防止把实现全塞进
调用方绕过任务。协议、原始提示、模型回复和停止理由见
[Agent 证据](../experiments/hia_agent_factorial_v4_20261028/results_20261028/README.md)。

资格选择使用三道独立 Rust 基线题，要求首次回复全部正确：

| 固定模型 | 基线正确数 | 请求/完整回复 | 已知 token | 整轮秒数 |
| --- | ---: | ---: | --- | ---: |
| Qwen2.5-Coder 1.5B Q4_K_M | 0/3 | 3/3 | 1,213 输入 + 313 输出 = 1,526 | 247.7604 |
| Qwen2.5-Coder 7B Q4_K_M | 0/3 | 3/2 | 1,213 输入 + 208 已知输出；超时输出未知 | 569.3217 |

合计已知 token 小计 2,947，实际 token 总量未知；不能把超时输出补成零。
总耗时 817.0821 s 是失败校准已经消耗的成本，期间可能共享开发 CPU，不构成
语言之间的公平耗时比较。

失败包括实际 Rust 类型/所有权编译拒绝、一次固定 240 秒超时，以及一份能
运行却产生 16/73 而非要求的 17/74 的回答。最后一份通过资源合同但功能错误，
再次显示安全检查不能代替任务正确性。未降低资格门槛、重试失败题或人工修复
答案；16 格主对照保持 **0 格尝试、0 次主请求**，未尝试格子不算作失败。

35 个参考/部分修复控制与 4 个对抗控制检查的是评估器行为，均不是模型成功。
本轮没有正确主任务，不能计算每个正确主任务的 token/时间、语言优势或长期
维护成本。需要新的预先声明的模型/工作流资格协议先取得足够基线成功，再在
冻结统一源码上执行主对照；本轮第五项成果尚未完成比较验收。

## 6. 强基线性能失败与 RSS 测量修正

filecheck 使用相同位运算 CRC 算法、字节布局和标量库 ABI；C/C++/Rust 允许
正常优化分配，分别真实执行 target-native、LTO 和 PGO 路线。PGO 使用独立
固定训练输入，各语言训练算法与字节数一致。Clang/LLVM 为 20.1.8，Rust 为
1.90.0；没有把 PGO 排除在 Rust 基线之外。
Rust 的插桩、训练、profile 合并和再次构建流程见
[官方 rustc 文档](https://doc.rust-lang.org/rustc/profile-guided-optimization.html)。

协议为 7 组 × 2 种 CRC × 8 个 arm，共 **112 个性能样本，0 排除**。整进程
时间从启动至退出，包含监控和 JSON 输出；P95/P99 是读取、打包、计算在内的
每批不超过 4,096 字节的分位数，不是端到端用户请求延迟。所有结果都是该
非独占 Linux x86-64 宿主上的描述性观察。

| 算法与比较 arm | 整进程中位数 ms | MiB/s | 批 P95 μs | 批 P99 μs |
| --- | ---: | ---: | ---: | ---: |
| IEEE：HIA native + LTO | 10.018746 | 49.90997 | 138.136 | 452.239 |
| IEEE：最快强基线 Rust native + LTO | 10.090064 | 49.55720 | 151.857 | 326.196 |
| CRC32C：HIA native + LTO | 11.500271 | 43.48030 | 149.417 | 641.208 |
| CRC32C：最快强基线 C native + LTO + PGO | 9.546028 | 52.38150 | 141.554 | 374.045 |

登记的 gate 要求两个算法的 HIA native + LTO 整进程中位数和批 P99 都不高于
各自最快实测强基线。IEEE 时间比 **0.992932**，P99 比 **1.386403**；CRC32C
时间比 **1.204718**，P99 比 **1.714254**。因此 gate=false。HIA 默认路线的
部分观察更好，但不能事后改选 arm 来替换登记的结论。

初始构建成本也已保留：HIA 默认 0.215164 s、HIA native + LTO 0.115279 s，
C LTO/PGO 0.159329/0.338725 s，C++ LTO/PGO 0.900627/1.579303 s，Rust
LTO/PGO 3.550847/8.062736 s。HIA native + LTO 是绑定已验证 IR 和实际 ELF
的研究构建路线，不冒充默认后端 receipt。小型按 8 字节分块且涉及分配的
位运算 CRC 也不是最佳可用 CRC 实现，不能代表各语言的性能上限。

### 事后 RSS 诊断没有替换性能样本

原 112 个样本的 `ru_maxrss` 均为 35,072 KiB。这不能用于证明各实现内存完全
相等。发现问题后单独登记了一个小型 C supervisor 诊断，保持原 driver、八个
库和输入字节不变，仅构建 supervisor，完成 48 个资源观察和 12 个启动控制，
共 **60 次真实执行**，checksum 与处理字节数全部正确。

同一 HIA 默认程序/IEEE 的三次中位数：普通 Python 直接启动为 47,528 KiB，
额外保持 64 MiB 已触页内存后变为 84,384 KiB；经 supervisor fork/exec 后
分别为 1,616 与 1,500 KiB。这支持启动进程历史峰值污染测量的解释，不声称
精确重建原 35,072 KiB 的每一页。48 个资源矩阵样本的完整子进程 wait4 峰值
范围为 **1,492–3,024 KiB**，每算法/arm 仅 3 次。
[Linux getrusage 文档](https://man7.org/linux/man-pages/man2/getrusage.2.html)
说明资源使用指标跨 execve 保留；本次还通过上述控制执行检验了这个测量问题。

这些 RSS 包含 loader、runtime、共享页面与剩余启动基线，不是 live owner
payload。它们是有限资源观察，既不能建立普遍优于 Rust 的结论，也不能证明
进程内存上界。原报告 SHA-256
`d8271f1aa20aecc8f47da773006246278ea13f2422f7e142b514f27047dae09e` 保持不变，
112 个原始性能样本零替换、零重算，原 gate 仍为 false。逐次数据与控制说明
见 [RSS 补充证据](../experiments/hia_filecheck/rss_diagnostic_20261028/README.md)。

## 8. 由本轮结果决定的下一道门槛

下一轮应继续维持 HIA Core 的明确语义和独立准入权，并把新增范围交给实证
门槛：迁移选择外部真实组件并计量人力；Agent 先取得预声明基线资格；NDU
实验要真正激活多个有收益且互相竞争的优化机会，记录完整探索成本；性能在
更大应用与明确宿主条件下复验，同时保留公平的 Rust/C/C++ PGO 基线。

NDU 可作为提出候选、分配优化预算和依据长期目标选择机会的层；每次实际变换
仍须满足已声明的等价、资源与发布条件。在未证明的范围内，目标应是“限定
候选集合与预算内可检查的改进”，不能把学习型规划器称为已保证任意程序每条
机器指令全局最优的编译器。当前证据足以继续工程研究，但尚不足以发布这类
普遍性承诺。
