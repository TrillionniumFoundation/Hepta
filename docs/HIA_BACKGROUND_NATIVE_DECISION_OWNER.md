# Complete native BackgroundOptimizer decision owner

The fixed six-word hia_background_decision_owner entry implements the actual ordered _decision path over the coordinator's owned values. It combines the qualified pure decision stages with actual value retention and lookup, lossless capture, checked canonical freezing, streaming HIA SHA-256, and two complete native verify_program calls. It returns an independently owned complete candidate payload and its actual Core/input digests, or an owned typed original exception.

This is the decision component. It does not perform conditional publication, commit a cancellation token, run the background worker, or qualify the final installed release.

## Data and exact order

The input values are the actual private metadata, decoded accepted Job payload, actual native rank result, and observed ranking duration. The enclosing coordinator owns these JSON-domain graphs exclusively through the call. They come from the accepted immutable payload and the captured native rank engine; this interface does not add support for foreign Python objects, cyclic graphs, or non-string mapping keys that those sources cannot produce.

The owner first retains all four input capabilities. Metadata supplies the incumbent hashes, function and epoch. The epoch-plus-one value is computed by the actual unbounded integer value operation and copied as full decimal bytes; it is never clipped to a machine word. The ranking duration is the actual captured clock difference, represented by an integer capability.

The observations are canonically frozen and hashed before the report's initial bindings are checked, preserving the original error priority. Both entire private inputs and report are separately transported through the actual lossless value stream and freshly captured owned JSON arenas. No caller-supplied arena, digest or verified flag is accepted.

Pure stage 0 checks the original schema, incumbent, function, generation and observations bindings. A successful continuation freezes the report objective first and input objective second. The owner builds and freezes the actual bound-objective dictionary with the captured metadata, then hashes its bytes. Stage 1 performs the exact objective, type, cost, observation-sum and candidate-selection checks. A valid abstention returns without verifying an unused source.

An admission continuation locates the selected submitted source in the captured candidate order. Duplicate-last selection, invalid-key errors and complete collection scanning belong to the qualified decision stage. The owner then obtains the actual corresponding source value and freshly verifies it, before obtaining and freshly verifying the ranker's selected source. Both calls use the complete verify_program owner, including its original typed/raw checks and historical-v2 collision rule. The owner hashes the actual normalized Core spans. Stage 2 compares those digests and applies the original observations, calls, cap, runtime, uncertainty and exact margin rules.

The admitted payload preserves the submitted candidate's full HIAVCF01 original and Core spans. A composite candidate and a primitive ranking source with the same Core therefore retain the candidate's original input identity. The later runtime provider remains responsible for its own scalar-profile admission and actual conditional publication.

No additional aggregate 8 MiB limit is imposed on observations, objectives, capture arenas or digest input. HIA streaming SHA consumes bounded chunks under its established state contract. The original per-program limits remain mandatory inside each actual verification call.

## Exceptions and retained cleanup

Fixed decision rejections preserve their original exception class and full message. Dynamic KeyError messages use the qualified native Python string repr on the actual captured key, including surrogates and quote selection. Checked-freezer exceptions are converted through the actual value API into owned class/message records. Unicode span observations are retained as explicit fields in that owned JSON.

Actual verifier-driver errors are also converted through actual value import and lookups. Their class is fixed by the captured verification operation. The driver's generic E_DRIVER code is not used as the original HIA exception code; the owner recovers the original code from the verifier's complete, standard diagnostic message prefix. Final comparisons check original class, code when present, and full message. Arbitrary data dictionaries are never treated as exceptions by inspecting a class-looking string.

Successful value and payload drops are cleared exactly once. A refused drop retains its actual reference and the whole continuation. An admitted candidate or completed exception survives an explicit cleanup retry without re-running semantic stages. If the failure occurred before decision completion, cleanup can finish with a terminal failure and no replay; a new ordinary invocation is required.

Nested owners are retried only after an explicit qualified retained-cleanup result. An active dependency whose state is unknown remains quarantined. Actual close operations are not repeated after their descriptors are consumed; failed unmapping retains its mapping for explicit retry. The enclosing coordinator must preserve all captured context records and the sealed executable throughout this state.
