# Explicit HIA normalization development candidate

This owner is opt-in development work. Physical interpreter recursion and the
full foreign-object accepted domain are still not closed. Whole-owner
qualification, default selection, live migration and legacy deletion are false.

## Selected mechanism and dependencies

The HIA coordinator owns snapshot and structure decisions, canonical encoding,
the order of fixed foreign observations, materialization, exception-unwind
permissions and consumed request acknowledgements. Its four required mappings
are `program_normalization.hiaasm`, `core_json_bytes.hiaasm`,
`agent_binary64.hiaasm` and `agent_binary64_format.hiaasm`.
Materialization uses the independent eleven-function HIA input
`tools/hia_program_normalization_materialize.hiaasm`, composed by its explicit
import/export loader before ordinary whole-Core verification.

Protocol `hepta.hia.program-normalization-native.v4-development-permanent`
removes the unused required packet image and the dead hosted packet decoder.
The independent nominal JSON codec, source, tests and all old observations
remain retained. This revision does not reinterpret the five formerly held
mappings as five executed mappings. The raw-front adapter still offers its
separate front-plus-nominal API; the normalization owner uses only its
canonicalizing entry.

The fixed note/delivery bytes are emitted by the HIA packer
`cpython_note_packer.hiaasm`. They call four pinned CPython APIs and remain a
hosted interpreter mechanism. The producer removes C compilation from the
production path; it does not remove CPython, object-representation primitives,
diagnostic primitives or physical C-stack behavior from the runtime.

Admission is explicitly restricted to CPython 3.14.4 with the GIL on the
existing Linux x86-64 LP64 native loader. Other interpreter versions refuse
before reading a selection manifest or mapping executable code. Actual
interpreter and exporting-image bytes are separately pinned by the note bridge.
No 3.12, 3.13, 3.14.10 or free-threaded equivalence is claimed.

## Build and source custody

`tools/build_hia_program_normalization.py` takes an existing compiler, cold
report and exclusive output path. It runs the shared complete-source cold
admission before creating the output directory. Every declared owner, authoring
fragment, test and HIA build input must occur in that actual source map.
Compilation uses unchanged `compile_stage` bounds; the HIA note packer emits
the fixed image through unchanged native invocation limits.

Exact integer types, source/compiler/image hashes, child receipts, receipt
readbacks and every final manifest/report readback are checked. The builder
rereads all consumed inputs, immutable outputs and the complete current source
map before and after publication. It never upgrades a predecessor-compiler
receipt to a matching-source cold result.

Persisted compile and emission receipts are independently admitted after JSON
parsing, then compared with type-preserving JSON encodings of the actual child
responses. Duplicate fields refuse. The retained standalone front and nominal
codec builders apply the same strict persisted-receipt admission and recheck
their complete source map, consumed inputs and earlier publications after both
final writes. Controlled transport tests cover integer-to-boolean corruption,
duplicate fields and input/receipt/manifest changes at the publication boundary;
these tests are not native compiler or cold-run evidence.

Installed admission recognizes the old explicitly development producer receipt
without changing its scope. A new
`hepta.hia.cpython-note-packer-production.v2` receipt additionally binds the
actual packaged complete-source contract, current owner HIA inputs, note source,
compiler receipt and emitted bytes. No authoring import is needed after
installation. This selection remains a trusted operator code capability,
not an all-input equivalence proof or release promotion.

Production build example, only after a real current-source cold report exists:

```sh
python -m tools.build_hia_program_normalization \
  --compiler /owned/current/B3.image.bin \
  --cold-report /owned/current/cold.json \
  --output /owned/new-normalization
```

This independent r9 revision has no such combined cold qualification yet.

## Permanent controls

`tests/test_hia_program_normalization_native.py` contains Source, Adapter and
Native classes. `tests/test_hia_cpython_note_packer_native.py` contains independent
source/VM and actual native classes. The retained test fixture stores complete
original source texts with individual hashes; only exact definitions and
control blocks execute. The original 78 and 14 controls, including the original
misnamed Mapping-as-key case, remain unchanged. Four separately named actual
large-key controls preserve the distinction.

Native fixtures require exactly one of
`HEPTA_HIA_PROGRAM_NORMALIZATION_COLD_REPORT` or
`HEPTA_HIA_PROGRAM_NORMALIZATION_DEVELOPMENT_MANIFEST`. They never silently
bootstrap or skip. An optional
`HEPTA_HIA_PROGRAM_NORMALIZATION_EVIDENCE` root receives an exclusive directory
per class; collisions refuse instead of overwriting earlier observations.
Development manifests remain development evidence. Tests check their inputs
again after execution.

The six producer-admission controls retain their original refusal assertions;
their setup now supports both explicitly distinct producer schemas. New
controls cover exact issued objects, no replay after refusal, removal of the
unused packet dependency, unsupported interpreter rejection and input/output
custody. The wheel control builds outside the source checkout, forbids
authoring imports, uses empty PATH for the application, and requires missing or
modified installed resources to refuse even after a warm mapping.

GNU assembly and historical C compilation occur only in independent test
references. The original 35 note/delivery controls run against HIA-produced
bytes, including actual kernel permission faults and the old bridge's retained
lifetime negative control. No mechanism result establishes physical recursion.

The ordinary Core interpreter observes the note packer's original three-buffer
entry directly and compares every output byte. It does not create a synthetic
assembly function with one returned scalar per output byte, which would exceed
the unchanged 256-item assembly-list limit for a 298-byte image. Source and
Adapter controls may run on another interpreter, including Python 3.12; their
scope does not qualify the CPython 3.14.4-specific note/delivery ABI. Native
fixture admission always enforces the actual interpreter requirement.

## Remaining integration and semantic work

The root integration must union every new source/fixture/fragment into the
complete contract, add package resources to the explicit lists in
`hepta/hia_agent_contract.py`, and include source/native classes in the actual
workflow and full retained harness. `setup.py` copies those explicit lists;
`tools/hia_selfhost_resources.py` is an independent VM resource-case corpus,
not the package resource registry.

Checker identity must bind the actual four held mappings, complete source
closure, note/delivery bytes, producer receipt and actual interpreter/exporting
images. The worker helper v1 does not acquire this multi-image capability by
accepting ambient manifests. It must either receive a complete explicit
capability or refuse the unsupported scope.

A fresh combined source freeze, source gate, unchanged 180+3 cold gate,
installed/native groups and full retained regression remain required.
Separately, near-Python-frame and actual C-stack callback/recursion equivalence
remain open. The original near-recursion task has an unknown acknowledgement;
a new host observation must not overwrite or reclassify that original task.
