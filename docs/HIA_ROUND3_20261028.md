## 1. 统一执行核心与明确拒绝

本轮没有引入第二套能够绕过 standalone HIA 的执行语义。新前端、历史 IR 适配、优化提案、CLI 和运行时版本都必须进入原有的 `verify_program`；值、资源、错误和效果的实际执行仍由同一 Core 决定。

| 输入或路径 | 实际去向 | 范围与拒绝边界 |
| --- | --- | --- |
| Hepta 源语言 | `hepta-source → standalone HIA` | 当前可检查的有限源语言子集 |
| 历史 executable / scalar / composite IR | 显式适配并重新检查 standalone HIA | 需要的原始源码与身份缺失时拒绝；不猜测版本 |
| C 迁移 | 已捕获子集 → Hepta → standalone HIA | 不接纳一般任意指针程序 |
| C++ 项目 / 配置矩阵 | 项目捕获 → 每个声明的去向 → standalone HIA | 每个已声明配置都检查，不能通过选择一个配置隐藏另一个错误配置 |
| 新 `std::unique_ptr<byte[]>` 路径 | `cpp-unique-project` / `cpp-unique-matrix` | 默认 deleter、精确 wrapper 和受限组合资源模式 |
| Rust / TypeScript / Python / Go / 原始汇编源码 | 无源语言前端 | 明确拒绝；语言思想、接口和未来适配设计不等于已经实现前端 |
| 解释器 / direct LLVM | 同一个已检查 Core | 解释器与原生资格分别验证；实际执行资格限已测目标 |
| 历史 Rust/C 后端、资源 IR、HMIR 等 | 显式参考、导出或侧条件 | 不作为隐式替代的部署权威 |

新增 CLI：

```text
hia import-cpp-unique-project
hia import-cpp-unique-matrix
hia optimize-narrowed
hia verify-narrowed
hia build-narrowed
hia optimize-guarded-narrowed
hia verify-guarded-narrowed
hia build-guarded-narrowed
```

对应实现见 `hepta/hia_routes.py`、`hepta/cli.py`。本轮实际原生平台是 Linux x86-64；不能把 LLVM 能够输出其他目标对象，等同于已经在那些硬件上执行并验证。

## 2. 优化必须携带可检查的义务

新增 unsigned modular narrowing 将最终截断向可证明的 wrapping 算术、bitwise 和 cast 内部传播。例如，可以提出把 `u8(u32(index) +wrap seed)` 改写成 `u8(index) +wrap u8(seed)`。

提案本身没有部署权。实现登记每项改写，并从原 Core 与完整登记表重建候选；独立 checker 对实际候选检查值、效果及 first-trap 等价。原来的 checked 运算仍保留，不能借优化删除可能先发生的错误。未知运算、额外修改、资源变化、重复或缺失改写、SSA 冲突、错误代数、拼接的中间 Core 都不能取得许可。

`guard → narrowing` 组合逐阶段绑定原始、中间和最终 Core，并共享一个整体 deadline 和证明义务预算。完整组合默认最多 30 秒；调用者给出较小预算时仍按较小预算执行。SAT、unknown、超时和预算不足均拒绝，不能因为模型或 NDU 认为有利而继续发布。

最终构建重新检查提案并绑定实际 ELF、Core、目标、checker、solver 与编译器身份。执行时检查 sealed memfd 中的字节，并核验实际函数地址所属映射，而不只检查一个可变文件名。

本轮独立 narrowing 测试为 12/12；small-guard 原生资格验证完成 288 项实际返回值比较。该资格使用 guard maximum 32，包含 30 项 guard 义务和 118 项 narrowing 义务，均为 UNSAT。反汇编可见 byte `paddb` 路径，每轮仍处理 16 字节；没有 32 字节向量化的声明。完整细节见 [HIA_MODULAR_NARROWING.md](HIA_MODULAR_NARROWING.md) 及 `experiments/hia_narrowing/round3_20261028/`。

这仍依赖 Core 语义编码、Z3、LLVM、链接器、加载器、分配器、OS 与硬件。它没有证明一般 C++ 源程序到 Core 的 refinement、整个后端的机器码 refinement，或整个工具链的绝对安全。

## 3. 八种构建配置与五种强语言基线：有限门槛首次全部通过

这是一项独立登记的新实验。它使用新固定输入分布、两个内核、七组配对观测，比较 original HIA、guarded HIA、guarded+narrowed HIA、Rust O3/fat LTO、C/C++ O3/full LTO 和实际训练后的 C/C++ PGO/LTO。没有将前一轮负面结果改写成通过，也没有因看到结果而重跑或删样本。

一次执行保留：112/112 样本、1,344 项原生正确性检查、3,472 个 batch 观测、28,784 个实际单次调用观测、7,280 个原始时钟观测，以及四次真实 PGO training invocation。全部 14 项预注册不劣门槛通过，其中 10 项对应五种强语言配置。

下表是候选 / 基线的配对耗时几何均值比，越小越好：

| 内核 | 原始 HIA | guarded HIA | Rust O3/LTO | C O3/LTO | C++ O3/LTO | C PGO/LTO | C++ PGO/LTO |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `full_lifecycle` | 0.507975 | 0.767302 | **0.787363** | 0.791619 | 0.786065 | 0.675813 | 0.773208 |
| `packet_xor` | 0.426624 | 0.572466 | **0.556401** | 0.566869 | 0.534381 | 0.535553 | 0.573329 |

相对该 Rust 实现的耗时降低点估计为 21.3% 与 44.4%；对应单侧 95% 上界为 0.853456 和 0.589771。每个上界使用七组配对 log-ratio 的 t 界，依赖独立、近似正态等假设。14 个判定的合取不是经过多重比较校正的总体 95% 置信声明。

**尾延迟并非全面改善。** `full_lifecycle` 的整批 P99 相对 original HIA、C LTO、C++ LTO、C++ PGO 发生回退，最高为 C++ LTO 的 **1.698142 倍**。batch P99 一开始就是保留的诊断量；门槛包括 batch P95 与实际单次请求 P95/P99，不能事后改变这一解释。相对 Rust 的单次请求 P99 比为 0.527562 与 0.447905。

峰值 RSS 相对 Rust 为 0.812261 与 0.817204，但这是包含 harness、加载器和库的进程 RSS，不是 owner 堆字节数，也不是普遍资源管理优越性的证明。

## 4. 真实 C++ 默认 deleter 资源模式迁移

新增实际 `<memory>` / `std::unique_ptr<unsigned char[]>` profile，包括零初始化数组、默认 deleter、构造中抛异常后的成员清理、移动、默认析构、受限访问，以及组合 owner 的跨 TU 按值转移。它自动生成独立 HIA 实现，不链接原始 C++ 对象。

| 配置 | 实际对照用例 | owner 分配 / 释放 | 分配拒绝 | 最终存活 | 项目声明出现次数 | 标准库声明出现次数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| three_weight | 437 | 401 / 401 | 196 | 0 | 139 | 92,058 |
| five_weight | 437 | 401 / 401 | 196 | 0 | 139 | 92,058 |

每配置迁移两个项目自由函数实现，并处理声明的组合资源结构和跨模块生命周期。外部桥接函数为 0；标准库实现体迁移为 0；通用 C++ 源程序等价证明为 0。标准库的 92,058 次声明出现都被明确列为 dependency-only，不当作已迁移实现或已证明声明。

完整 Clang AST 大约 233 MB。初始整体载入曾失败，保留了该开发记录。最终捕获使用有总量、子树、深度、值数量和时间上限的流式读取，消费到完整 EOF，记录所有声明，并在超时后清理所属子进程组。实际标准库展开与去掉项目覆盖参数后的编译器参考展开比较；特殊 deleter、改变标准库语义的宏、遗漏配置、缺定义、未知活动声明、移动后使用与未建模释放都会拒绝。

标准库默认 deleter 的语义仍是显式受信契约，不是标准库实现的自动证明。支持 LP64 / Clang20+ 的限定模式；不涵盖任意模板、custom deleter、shared ownership、指针逃逸、任意异常 ABI 或完整 C++ 对象布局 ABI。

本地迁移计时 82.531603561 秒；包含迁移的资格检查为 88.966702589 秒，两者不能相加。报告进程与子进程峰值 RSS 各为 196,768 KiB。启动、最终报告写入、归档与人工成本分别说明；这不是通用“极低成本迁移”对照实验，也不是该模块的速度优势证明。

完整 67.6 MB 原始资格 JSON、清册、源身份、生成 Core/LLVM、原生产物、用例和命令输出在无损归档中。完整原始 AST 流未归档；保留完整流哈希、长度、EOF/census 和捕获输入。Clang 进程局部地址可能变化，不能承诺再次捕获得到逐字节相同的原始 AST。

本地 qualification02 绑定后续运行时清理之前的完整编译器快照。最终源代码 CI 已重新执行迁移与拒绝检查；二者的身份和平台结果分别保留。详见 [CPP_UNIQUE_PROJECT_MIGRATION.md](CPP_UNIQUE_PROJECT_MIGRATION.md) 以及 `experiments/cpp_unique_project_eval/round3_20261028/`。

## 5. NDU：复用真实原生进程，仍由独立验证器决定准入

原生来源是 `hepta-private-ci` 的准确提交 `c4a1bbed3a39beba43a6abf1a18b6f75c5725c21`，tree 为 `abb5fed3299476f28a55980e9c4b35e3ee32cab3`。新增 `--stream` 身份握手和最多 256 个顺序请求，每帧最多 1 MiB。编号、请求、目标、快照、generation 和原生身份必须一致；部分帧、超限、错误、超时均终止该进程，不能从失败会话继续取结果。

每次仍调用原来的 Rust NDU 评估器，没有 Python 评分仿制，也没有缓存旧决定。Python 端执行 sealed memfd，并检查实际 `/proc/<pid>/exe` 的映像身份；PID namespace 与挂载的 proc 不匹配时明确拒绝，未削弱检查来兼容不支持的环境。

`authority: DENY_ALL` 与 `safety_certificate: false` 不变。NDU 可以建议有限候选的序列，不能签发代码安全证明。候选重新经过证明、构建、最终字节绑定和实际测量。

准确发布源码的 empty-target 原生构建为 **45.995841701 秒**，复用已有依赖源缓存；不是整台机器完全冷启动。本地二进制 SHA-256 为 `ce5ff4fc53ce8f47172bc80b9425acd73a5a39d68dd019261e6e1dbe5bc074cd`。独立 CI 也执行 8/8 Rust 协议测试，实际 CI 二进制有自己的身份，不能混同为本地测量二进制。

新实验事前登记 3 组、6 个控制策略、每次 524,309 调用、批规模 `[223, 49157, 65521]`；增加已证明 guarded+narrowed 候选。较大 horizon 的选择明确受到先前负面成本和本轮独立性能实验准备成本的启发，发生在该新图实验的任何 workload 之前。

所有策略取得同一完整候选测量信息，使用同一 120 秒 episode 预算。强固定策略选择并提交完整最小成本计划；轻量控制执行完整有限时域动态规划。强控制不用承担 NDU 特有的编码开销。最终净收益门槛读取全部组的实际 standalone total，不让一个有利中位数掩盖昂贵组；外层注册、身份和证据开销还作为明确的保守附加费用计入 NDU。

该完整 DP 已经求解同一供应代价模型。因此，即使 NDU 在有限测量中通过，也不能直接推出一般性搜索优势，更不能推出任意程序每条指令的全局最优。

### 实际闭环与负面净收益结果

一次执行完成 **18/18 episodes、72 次 workload 观测、36 次候选校准观测**。全部实际输出正确、episode 预算通过、输入身份保持。无 guard 的候选被独立验证拒绝。所有策略合计实际重新证明/构建并切换版本 **15 次**；其中 **NDU 自身 3 次**，每组一次 `base → guard-wide`，后者包含 guard+narrowing 链，随后读取实际测量并选择 stop。其余 12 次属于固定或轻量控制，不能算成 NDU 成绩。

真实 native stream 共处理 9 次评估请求并正常关闭，最终执行映像仍是登记的 `ce5ff4fc…`。原生构建 45.995841701 秒真实计入 NDU，公共校准每个 standalone 策略只计一次；wrapper 的 0.268808420 秒另保守地加给 NDU。

| 策略 | 三组完整 standalone 成本 | 相对 NDU 的净节省 |
| --- | ---: | ---: |
| 强固定完整计划 | 348.754475126 秒 | **49.703041760 秒** |
| 轻量完整动态规划 | 352.591082376 秒 | **45.866434510 秒** |
| NDU，含其 wrapper 附加费用 | **398.457516886 秒** | — |

## 7. Agent 开发实验：相同预算与真实失败

新实验固定两个独立的小型量化模型家族，四项新任务，两项维护、两项 API 升级，每项均提供完整两文件工作区。HIA 与 Rust 使用同一模型、工具预算、公开案例、隐藏 oracle 和回答外层结构约束；每格最多两次、每次 2,048 输出 token、180 秒。结构约束只限定文件包外层和文件名，不编码答案、运算或常量。

所有第一次公开通过的提交，只在事后执行一次隐藏边界/随机案例，隐藏错误不给模型反馈。provider 必须独立满足自己的契约，并被 consumer 按原参数调用恰好一次。Rust 使用可信 native wrapper 计数；HIA 使用同一 Core 的 VM trace 和独立 native entrypoint，不把它称为 native HIA 计数器。

预注册控制包括 24 项参考资格、6 项敌对提交和 12 项编排/准入控制；这些不是模型成功率。实际模型调用、错误提交、修复、超时、进程重启、验证及 token 均分别保留。未知输出不填零。

两个家族均完成各自全部 8 格：Qwen2.5-Coder 1.5B 正确 **0/8**，16 次请求、15 个完整响应、一次超时；Granite 3.3 2B 正确 **0/8**，14 次请求、11 个完整响应、三次超时。合计 **16/16 格已尝试、0 格正确，30 次请求、26 个完整响应、4 次超时**。每个家族的维护与升级门槛、跨家族门槛均未通过。超时按冻结协议终止该格，其后为下一格启动新进程；没有额外重试来补齐成功。

26/26 个完整响应实际通过了 `files` 外层校验，但内容仍分别遭到语言 profile 拒绝、编译拒绝，或在真实原生执行时得到错误结果。Qwen 的 16 次提交分为 8 次实际 `observable_wrong`、5 次 `response_rejected`、2 次 `compile_rejected` 和一次 timeout；其中 Rust 的 `wide_product_tag` 两次被 rustc 以 provider 参数类型不匹配拒绝，不能统计成已执行的算术错误。Granite 两次写出 `.extend(128)`，在受限 Rust profile 中被拒绝、未进入编译；这种准入拒绝不能改写为模型程序运行后错误，也不表示该方法实际属于 primitive 整数接口。

最终全部提交的互斥分区是 **14 次实际输出错误、10 次 profile/准入拒绝、2 次编译拒绝、4 次超时**。14 个候选完成原生构建并执行公开校验，但没有一个通过公开校验，因此隐藏校验实际执行次数为 **0**，不能把预先准备的隐藏 oracle 算成已经得到隐藏泛化结果。26/26 个完整响应均满足外层 envelope；13 次保留原 provider、12 次保留原 consumer，10 次第二回复逐字重复。这个新实验已排除上一轮缺 `files` 外层的直接问题，仍没有得到正确完成。
