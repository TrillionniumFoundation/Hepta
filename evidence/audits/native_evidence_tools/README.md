# Independent native/proof/debugger evidence audit

The audit started from `d173096`, after the C physical-line mapping fix. All
three original producers completed an actual successful local run: the pinned
Lean kernel, GCC/Rust bidirectional ABI driver, and GDB on both backends.
Those source/compiler identities are preserved in `baseline-*.json`; they are
historical observations, not qualification for a later compiler snapshot.

Fifty malformed or inflated report variants were evaluated against the original
validators. **41 were unexpectedly accepted.** The main gaps were:

- Memory proof validation did not bind the theorem dependency map to retained
  kernel output and ignored the checker version and the stated proof scope.
- Host validation accepted missing host/compiler identities, compilation/run
  commands, header/driver hashes, object source identities and complete frontend
  checks. Two missing artifact hashes compared equal to one another.
- Debugger validation did not verify the source map or step observation and did
  not compare the structured observation to the actual GDB transcript. A pair
  of fabricated breakpoint file/line fields could therefore agree with each
  other while disagreeing with the run.
- Python equality allowed integer/float substitutions for some boolean and
  integer schema values.

The hardened producers were executed again on the same isolated code snapshot.
The new validators accepted those actual runs and rejected all 50 corresponding
mutations: **0 unexpected acceptances**. `after.json` binds the exact updated
validator sources, and `after-*.json` retains the real regenerated evidence.
These reports retain the original isolated source/compiler identities. The
final integrated release must run its own full gates; these audit runs do not
qualify later edits.

The reusable cases are in `tests/native_evidence_cases.py`. The three tests in
`tests/test_native_evidence_validators.py` produce fresh actual evidence before
applying the cases, so they cannot pass merely by rejecting a stale baseline.
Malformed top-level inputs additionally must produce `ValueError`.

## Strengthened contracts

The memory gate now requires the successful kernel exit, complete unique
kernel dependency records, exact checked-source/output hashes, and agreement
between the printed axioms and the reported theorem map. Each broken mutation
must reach the intended theorem and show its failed proof dependency, alongside
the nonzero exit and full diagnostics. The exact declared scope is validated.

The host gate regenerates the exact matrix, header and Rust source/probes,
binds the native frontend and final object to them, checks compiler identities
and compatible actual-host target triples, and requires all eight recorded
compiler/linker/driver commands. Both optimization rows must correspond to their
actual raw driver output. The wrong C echo must have the exact mutation hash and
fail its own scalar assertion after successful compilation/linking.

The debugger gate retains generated source text and the full GDB script in the
report, allowing inspection even after its temporary executable directory is
removed. It reconstructs the actual source map, checks native source/artifact
identities and debug flags, requires the intended three stack frames and live
locals, and reparses the raw `HEPTA_DEBUG` observation. Actual stepping must stay
in the intended file and reach the return statement or the known Rust function
epilogue. Rust's epilogue attribution is explicit; no original-Hepta DWARF claim
is inferred from generated Rust line information.

## Formal scope review

The 19 theorems describe an explicit mathematical model. The expression core is
closed, has wrapping 64-bit arithmetic, and proves progress/preservation; it
does not describe every source type or checked-overflow operation. Allocation
identities and generations are caller-supplied natural numbers. The model has
no allocation constructor that establishes global freshness or unforgeability.
Loan admission preserves pairwise compatibility; it does not establish the
validity/liveness of each view. These limitations now appear in the validated
scope, alongside the absent AST/IR/backend refinement and foreign/hardware
proofs. The pinned Lean executable still trusts its installed runtime/imported
library; binary hashing alone is not a proof of that infrastructure.

The checks bind records generated by the local qualification programs. They
are not an authentication scheme for arbitrary third-party JSON reports.
