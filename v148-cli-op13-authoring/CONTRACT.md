## Production path and evaluation order

The caller explicitly admits a real PatchResult image and issues an opaque `PatchDefinitionRecord` before selecting this adapter. It also supplies the real preissued Inspect record already used by the R5 Inspect/report CLI. Selection never issues a record or imports a module to manufacture a witness.

`NativePatchInspectReportCli.prepare` calls the actual R5 prepare method, preserving the real report/discovery/parser chain. At op13, the original permission branch runs first. The adapter then captures `common['apply_program_patch']`, evaluates `value(a)`, and evaluates `argument(b, 1)`, in that order. Definition checks occur inside `invoke_captured_patch` after both arguments have been evaluated. It never looks up the public provider again. The returned pair is unpacked before either original register operation; revised program and receipt are registered in the original order.

The positive route invokes the actual `NativePatchResult.invoke_bound_apply`, passing the captured provider and original arguments. The existing HIA component implements both complete original bodies: `apply_program_patch` and `_check_patch_interface`. This adapter does not rewrite `_prepare_program_patch`, `selected_prepare_patch` or the existing Agent mode-2 byte engine. The business receipt still has `claims.native_executed == False`; invoking HIA policy grants no permission to change that field.

Other operations delegate to the actual previous closure. A changed report/Inspect closure also delegates op13 once through that previous closure. Missing, forged, stale or mismatched tokens call the already captured foreign provider once. An exception after native entry is never retried through that provider.
