# Actual R2 and R5 evidence: independent terminal data reader

## Facts and status

The R2 parent stopped after the ordinary eight VM methods because its original
buffer-reference reader rejected the actual five-field reference schema. Its
parent status stays FAIL. The later actual R5 owner ran all four original
lost-return methods and recorded their complete start/stop sequence, successful
child/wrapper reports, and complete 180+3 cleanup with ECHILD. The R5 parent
wrote its 48-reference VM readback and was then killed before its STAGE and
parent RESULT writes. The Root outer reported -9, no timeout, and complete
cleanup. No evidence identifies the reason for that signal.

This successor runs no product. It writes to a new terminal-readback directory;
it does not rerun the four methods, synthesize either missing R5 record, modify
the old R2 missing group, or turn either original attempt into PASS.

## Bounded large-metadata representation

The original large-predecessor code kept a whole STATE dict, a second current
metadata dict, all decoded shard rows, and path lists at once. The largest
actual predecessor has 55,798 files. This is a concrete aggregate-memory risk,
not evidence that it caused the R5 -9.

The new reader changes only the large evidence bookkeeping representation:

- The complete original STATE parser visits each original value and validates
  the same held/named file and full hash. Its mapping is a disk mapping.
- The original directory traversal, regular/directory restrictions, independent
  inode condition, and all seven stat fields are unchanged. The resulting
  mapping is on disk, with the original per-directory sorted entries retained.
- The fixed shards retain the original 4MiB capture limit. Each shard is read
  fully and decoded separately; its rows append to a disk sequence. No list of
  all shards' rows is materialized.
- The full ordered-row object uses the original canonical JSON formatting and
  two complete encodings. Both full SHA-256 passes, length and Git blob identity
  remain checked, with a disk sequence replacing only the in-memory sequence.
- Original complete row-path ordering is compared as two complete iterators.
  Every regular row then invokes the original streaming full-payload reader.
- Full current path/stat inventories before and after remain equal to the
  complete frozen STATE. No row, file, comparison or exception is skipped.

The Ledger/DiskMap/DiskSequence/JSON helpers are copied whole from the actual
previous R3 data reader. SQLite is used only as this reader's private metadata
index, with cache8MiB, mmap0 and temp FILE. It is not a production Store change
or a payload cache. Only metadata is in the database and full-read ledger.
The new functions retain the original 16MiB per-value and per-file capture
limit and all original source/runtime helpers. This is not a claim of constant
total memory: source maps, a single bounded shard, JSON values, sorted entries
within one directory and the original frame-reader's bounded objects still
exist in memory.

The original 1GiB free-space admission remains. An estimated additional 768MiB
of private metadata space is documented for scheduling, not a budget increase
or a replacement for the actual floor. No old evidence is retired.
