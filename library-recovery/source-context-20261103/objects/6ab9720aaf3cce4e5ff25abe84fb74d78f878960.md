# HIA v0.1 — Hepta Intelligent Assembly

**状态：架构研究 RFC，非实现完成声明。** 2026-10-26。推荐仓库：<https://github.com/TrillionniumFoundation/Hepta>。

## 0. 决策摘要

建议将 HIA 定义为面向 AI Agent 的 **可验证、低级、类型化虚拟指令集**（a typed, proof-aware, agent-editable virtual assembly ISA），而不是新实体 CPU ISA。HIA 是原生代码生成前的规范化可执行语义层：`HIA core -> LLVM/MLIR -> CPU/GPU ISA`。无需垃圾回收器、Python VM 或 JavaScript VM。性能目标为与等价 Rust 本地代码在相同优化条件下相当，在特定工作负载中通过算法和目标优化胜出，而不是声称普遍更快。

**新组合假说：** 可执行 SSA + 所有权/借用/内存效应 + C/C++ 互操作 + 独立检查证明 + 事务化 Agent 语义修改 + 确切机器代码来源。每个点有先例；新颖性在统一、低成本、安全的工程闭环，需要实验验证。

**不可违反：** C/C++ 源码翻译得到的 unsafe/raw pointer/foreign contract 不得被自动标为 proven safe；内容哈希与签名只证明身份，不证明语义；模拟/跨架构 object 不等于实体运行；`checked` 不等于全项目功能等价；GPU、真实设备资格不能由 CPU 测试替代。

## 2. 目标与非目标

目标：

1. 可扩展、明确操作语义的基本块 SSA 汇编；每个数据 SSA 值单一定义。
2. 所有权 `own<T>` 是不可隐式复制的线性对象；共享/独占 `loan<T,'r>` 有可静态验证的生命周期及别名限制。
3. 明确的类型、可用地址空间、布局、初始化、内存来源（provenance），以及读写/atomic/foreign 等内存效应 token。
4. 证明义务、资源合同、外部假设以及授权的边界显式可审计。
5. AI 局部修改是语义操作，带原始源码、接口、目标、编译器、合约身份；独立验证前不得发布机器码。
6. C 原生 ABI 可用；C++ 通过 ABI 桥、按目标兼容和渐进源码转换复用生态；独立测量具体配置。
7. LLVM 后端优先，MLIR 多模态/张量/GPU 支持后置。

非目标：

- 不重造 x86/ARM/RISC-V 硅片或要求处理器硬件直接解码 HIA。
- 不复制 TypeScript/Python/Go 的 GC 或解释器作为高性能程序运行时。
- 不承诺任何未知 C/C++ 程序自动翻译后完全安全、ABI 等价或行为等价。
- 不承诺无 `unsafe`/FFI/硬件信任边界，或普遍跑赢 Rust。

## 3. 单一语义权威与中间表示

```text
C/C++ compilation database -> Clang AST -> compatibility dialect ---+
Rust/frontends ----------> validated source / canonical HSIR ------+--> HIA Core (single semantic authority)
Agent spec/patch ----------> typed obligations and checked edits ---+
                                                                      |
                                      independent owner/CFG/value/effect/provenance verifier
                                                                      |
                                                    verified HIA canonical SSA + proof receipts
                                                       |                           |
                                                LLVM/native CPU            MLIR/GPU/device
                                                       |                           |
                                               x86-64/AArch64/...         actual target ISA
```

同时有三种互不冒名的文件：

- `.hia`：规范文本虚拟汇编，版本确定且可唯一规范化。
- `.hiab`：紧凑的版本化二进制编码及内容哈希；与文本 round-trip 对应。**v0.1 仅规定要求，不规定现成编码格式。**
- `.hiaproof`：审计证据、外部边界、推导规则和回执；只有独立验证器认可的定理才可用于安全升级。

AI 编辑建议使用带预期 project/content/interface/proof digest 的语义操作，不能直接更改“已经证明”的字段并通过重算哈希伪造证明。所有证明状态按强类型、闭合 schema 校验。原始输入由真实 source re-derive，不依据自报状态。

## 4. HIA Core 指令语义（提案）

一个函数含 `type`, `layout`, `abi`, `effect` 与 `resource` 声明；基本块有参数，可表达 phi；数据 SSA 值只有一次定义；Owner/Loan/Effect capability 是独立线性域，在控制流合并处验证许可余额与生命周期。`prove.*` 为静态检验或自动化推导，不能当作任意可造的值。

| 指令族 | 例子 | 验证要求 | 运行成本 |
| --- | --- | --- | --- |
| scalar/vector | `i.add.wrap`, `i.add.checked`, `icmp`, `fadd.strict`, `simd.shuffle` | 精确位宽、溢出、NaN、目标特性 | 原生计算或指定 trap |
| control | `br`, `condbr`, `switch`, `ret`, `trap`, `invoke` | terminator 全覆盖，SSA dominance，edge join | 原生分支 |
| layout/place | `place.field`, `place.index`, `layout.of`, `addrspace.cast.checked` | 路径、尺寸、对齐、来源 | 常见情况编译期消除 |
| memory | `mem.load`, `mem.store`, `mem.init`, `mem.copy.noalias` | 初始化、访问长度、permission、顺序 | 目标 load/store 等 |
| ownership | `own.move`, `own.split`, `own.join`, `own.drop` | 不重复消费；正常/错误边完整 | 编译期为主；析构真实执行 |
| borrowing | `loan.shared`, `loan.unique`, `loan.end`, `loan.reborrow` | 生命周期、冲突借用、跨 CFG 与调用约束 | 静态可消除的 loan 零运行成本 |
| effects | `effect.chain`, `atomic.rmw`, `atomic.fence`, `io.call` | 强/弱内存顺序，副作用排序 | 同等硬件操作 |
| ABI/foreign | `abi.c.call`, `abi.c.export`, `abi.cpp.bridge`, `foreign.assume` | 目标编译器、布局、异常、外部 ownership 合同 | 可直连或桥接开销 |
| hardware | `arch.x86.*`, `arch.arm.*`, `mmio.read.volatile`, `dma.map`, `irq.bind` | 目标/privilege/capability、地址空间及设备合同 | 精确目标指令/必要屏障 |
| agent/proof | `require`, `ensure`, `assert.verify`, `spec.hole`, `cost.contract` | 静态审计/证据；不得从提示升级为证明 | 能擦除的元数据不进入热路径 |

原生汇编逃逸：只允许带目标特征、输入/输出、clobber、内存效果和 `unsafe` obligation 的专用片段；其安全性**不会**因标注而自动得到证明。要从 safe HIA 调用，须有已审核/已验证的安全 wrapper。

## 5. 规范文本示例：整数切片求和（**提案语法，不是现有 0.2 编译器可运行源码**）

```hia
module @math;
profile hia.core.v1;

func @sum_u64(%xs: loan.shared<slice<u64>, 'r>) -> u64
  effects {}
  resources { heap_allocations = 0; may_block = false; may_spawn = false; }
{
^entry:
  %n: usize = slice.len %xs;
  %zero_i: usize = const 0;
  %zero_s: u64 = const 0;
  br ^loop(%zero_i, %zero_s);

^loop(%i: usize, %sum: u64):
  %ok: bool = icmp.ult %i, %n;
  condbr %ok, ^body(%i, %sum), ^exit(%sum);

^body(%i1: usize, %sum1: u64):
  %inbounds: proof<%i1 < %n> = refine.true_edge %ok;
  %x: u64 = slice.load %xs, %i1 using %inbounds;
  %next: u64 = i.add.wrap %sum1, %x;
  %one: usize = const 1;
  %i2: usize = i.add.wrap %i1, %one;
  br ^loop(%i2, %next);

^exit(%answer: u64):
  ret %answer;
}
```

语义：`slice.load` 的入界证明来自已经校验的真假分支，不能凭 LLM 自行填入 `proof`；`%xs` 共享借用在调用期间不被可变别名改写；数据取值按 u64；累积使用 modulo-2^64 环绕而非 C 有符号 UB；不分配、不阻塞。`refine.true_edge` 是静态证明（ghost）指令，编译后无需执行；如不能证明入界，拒绝或生成明确 guard 和 panic/effect，并同步修改函数 contract。

## 6. 形式化状态转换

程序状态包含：`(SSA values, heap, initialized places, owners, loans, provenance, memory tokens, device caps, external obligations)`。

核心规则：

```text
Γ; Σ ⊢ op : (T_inputs, R_in, E_in) → (T_outputs, R_out, E_out)
```

- `own.move`: 消费源唯一 owner，产生目标 owner，不能保留原活跃 handle。
- `loan.unique`: 必须由活着的 owner 或许可 reborrow 产生；拒绝任何重叠共享/独占冲突，或不符合地方分离证明的两次 mutable loan。
- `own.drop`: 释放拥有权并履行析构义务；活跃重叠 loan 令 drop 拒绝。
- `ret` / `error` / `unwind`: 所有可达且在规格范围内的退出边都必须交代 owner、loan 与资源；异常和取消必须在独立模型明确。
- `mem.load`: 证明地址关联有效 allocation/provenance、已初始化、布局、访问区间和权限；原始指针需要可信的动态条件或显式外部 assumption。
- `effect` token：同一可混叠内存和外部资源上的副作用顺序由 token 约束，优化不得错误重排或消除。
- `unsafe/ffi`: 外部 ABI、分配器、硬件、生命周期的条件在输出的未证明 obligations 中保留，不得通过优化器静默擦除。

可保证的目标是：在已明确定义的 safe 核心及可信编译器/平台假设下，排除相应类别的 UB（如 use-after-free、double-free、数据竞争等）。不宣称硬件失效、恶意编译器、未知 FFI 或操作系统缺陷不存在。实际语义健全性需独立证明或有限资格结果。

## 7. C/C++ 迁移及代码复用分级

### L0：最低成本立即复用

保持第三方 C/C++ `.a/.so/.dll` 原封不动。C 使用实际目标头文件+ABI 元数据导入；C++ 以原编译器编译的 `extern "C"` wrapper 或 target-locked C++ ABI profile 包装。自动生成 ownership/lifetime 约定的待审核 manifest。优点是几乎不用重写；缺点是 foreign trust boundary 未关闭。

### L1：语义兼容导入

`compile_commands.json` + Clang AST + 配置/宏展开归档 -> HIA `compat.c` 或 `compat.cpp` 方言。所有源声明和编译配置逐项核对，不丢失 varargs、bitfields、packed/align、volatile、restrict、atomics、inline asm、goto/longjmp、模板实例化、异常、虚表和对象生存期义务。对于无法表达的节点 fail closed 或保留可调用的原生桥，不能静默误译。L1 有运行等价的有限证明/差分测试，不承诺自动 memory-safe。

### L2：安全化重构

解析 Region/Owner/Loan；把裸指针尽可能转换成借用切片/拥有缓冲区；把 `malloc/free/new/delete` 的调用链配对；自动隔离仍需 unsafe 的边界；多条控制流路径及析构失败路径交由 checker/solver 验证。适合大小有限、封闭接口的 C 模块。可减少 unsafe 但不保证全部清除。

### L3：条件认证的安全原生替代

源码→HIA→机器码和原 C/C++ 在清楚定义的输入域比对内存效果、出错行为、C ABI、性能；加入 sanitizer/fuzz、静态 UB 分析、allocator fault injection、异常与对象生命周期测试、跨多目标验证。证明目标包含跨 IR lowering refinement 和外部库条件。只对指定源 SHA、配置、目标、已建模域授予 L3。没有覆盖的行为保留 unknown。

**C++ 迁移策略：** 优先重用对象库；保留目标工具链的类布局、mangled symbols、vtable、this adjustment、RAII destructor、exception/unwind、RTTI 和 STL runtime ABI。泛型模板可按 AST 实例化成具体 HIA 函数或调用既有实例化，不能声称保留跨编译器 ABI。Windows MSVC ABI 与 Itanium C++ ABI 分 profile 管理。不要将 C++ `std::string`、`std::vector` 当成稳定跨供应商 `repr(C)`。

### 转换器接口（提案 CLI）

```sh
hepta hia-import-c --compdb build/compile_commands.json --target x86_64-linux-gnu --output out/
hepta hia-bridge-cpp --compdb build/compile_commands.json --abi itanium --output out/
hepta hia-migrate --input out/module.hia --level L1 --emit-obligations out/obligations.json
hepta hia-safen --input out/module.hia --target L2 --emit-report out/safety.json
hepta hia-check --source out/module.hia --require-proofs --native
hepta hia-diff --original build/original.so --candidate build/hepta.so --cases frozen.json
```

这些命令只是 RFC 目标，不代表当前项目已支持。

## 8. AI-Native 指令及工作流（静态开发协议，不是运行时执行指令）

- `inspect`：按函数、effect、owner、call graph 和 ABI 提供切片化 context，避免整仓重复传给 LLM。
- `propose`：用稳定符号 ID、局部 SSA def-use graph、expected digest 和声明的 contract delta 发出机器可解析变更。
- `check`：完全重导来源→Core，独立执行类型/资源/效果/SSA/假设检查，报出局部失败原因。
- `prove`：SMT/Lean/Verus/有限模型工具只生成可验证证据；不能接受“LLM 说已证明”。
- `measure`：记录 token/tool calls/CPU/RSS/allocations/latency/p99/native asm diff；测量不自动证明产品质量。
- `commit`：多文件 durable transaction + optimistic concurrency + no-clobber publication + real crash recovery；先 validate 再发布；绝不越过权限边界。

图/证明/资源精度随层级严格分开：`syntactic_valid`, `typed`, `native_checked`, `runtime_differential`, `refinement_proved`, `hardware_qualified`，没有隐式向上升级。

## 9. 编译器实现策略

**短期：** 以现有 Hepta 0.2 及已审查的 PR 单一权威为起点，继续保留固定 rustc 作为参考路径。不要复制 Python parser、Resource IR checker、HIA scalar oracle、C/C++ migrators。确定 `hepta.hia.core.v1` 唯一 wire schema，明确定义 old `hsir.v0` adapter 无损/拒绝规则。

**中期：** 开发单一可执行 SSA 的 owner/borrow/effect/provenance verifier；LLVM CPU-native emitter 必须消费被实际校验的同一指令；Rust 参考结果、独立有限 oracle、原 C 实现一起做差分。确认安全后可将热路径 checker 和编译器迁至 Rust，以提高增量编译性能；Python 保留 Agent 工具胶水。

**后期：** C ABI 物理机矩阵、C++ 生态渐进迁移、专用 MLIR GPU dialect、RISC-V/CHERI-capability/memory tagging 实验、OS 裸机/设备 DMA/IRQ 合同。模型/设备专属 backend 必须有独立 target oracle 和硬件证据。

## 10. 验收矩阵：零假通过

| 阶段 | 硬门禁 |
| --- | --- |
| P0 语义 Authority | 唯一 canonical source/HSIR/Core，所有旧 envelope 明确映射或拒绝；不能存在相同 schema 名字不同语义 |
| P1 安全 | 正反例覆盖双重 move/drop、跨基本块 loan、返回悬垂、alias、未初始化、provenance、错误/异常退出、线程数据竞争；不能由自报 proof 通过 |
| P2 真正汇编 | 已验证 HIA Core 的独立解释器与 **消费同一 Core** 的 LLVM emitter；源码、Core、obj 的单向/反向身份全一致；核心不靠回退 Rust 做代码生成 |
| P3 C | 实际 C 工程、完整 TU/编译配置清单；ABI x86-64/AArch64 Windows/GCC/Clang/MSVC 按可用目标覆盖且缺项显式；失败/边界/UB 分类准确 |
| P4 C++ | 从 L0 逐层提高：类、模板、RAII、exception、STL、虚表及不同编译器/标准库 ABI 实例，禁止把 wrapper 称为安全重写 |
| P5 性能 | 同输入/算法/优化选项、等效资源限制，CPU/RSS/峰值、指令/分配、throughput 和 p50/p95/p99；报告回退与不稳定性，不使用未验证“超越 Rust”结论 |
| P6 Agent | 真实模型的 Rust vs Hepta source vs HIA direct 可比任务，同模型/预算/工具/seed/盲测；success/tokens/tool attempts/corrective edits/cost 全保留，fixture 不冒充模型试验 |
| P7 硬件 | 真机/设备 MMIO、DMA、IRQ、并发、掉电恢复、GPU 正确性/性能，明确验证的 ISA/驱动/OS/target triples |

性能的**提案门槛**（不是已有成绩）：在代表性负载的固定等价语义条件下，geomean latency 不明显劣于 Rust，性能回退 >5% 的个例必须定位；在 64/256/1024/4096 工作负载规模测 CPU、RSS、throughput、p95/p99 并解释预算；GPU 单独报告。不要用单一微基准推出全语言优势。统计置信区间和重复实验是必要条件。

## 11. 风险与技术决策

- **内存安全与汇编自由冲突**：safe Core 只允受控指令；raw ASM/FFI 用分层能力边界和独立验证。不能把 unsafe 放行当成可证明安全。
- **C/C++ 大规模自动转换存在理论和工程限度**：宏、预处理、不同 UB、复杂库/ABI 不存在通用无条件低成本 L3；L0 重用先行。
- **性能优势不是语法带来的**：来自良好 SSA 优化、布局、alias 信息、专业 kernel 和算法；否则可能不及 Rust。
- **同一概念多份 IR**：PR #14/#36 历史碰撞，以及 PR #164 executable core，都需要明确 single-authority 合并而非重复发展。
- **Agent 能力需被实验否证**：结构化语言也可能因训练数据稀缺导致模型输出错误率高；必须真实 A/B 验证。
- **恶意证明声明**：独立验真、schema bool 真正布尔、hash re-derivation、防 TOCTOU、原子发布、sandbox 编译器/分析器。
